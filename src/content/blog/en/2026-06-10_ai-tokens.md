With the rise of advanced AI assistants that work directly within our projects (such as *Claude Code*, *Cursor*, or local models running on your machine), the way code travels through infrastructure has fundamentally changed. We no longer write code just for humans and the computer to execute. It has become text that we constantly stream over the internet into the brains of Large Language Models (LLMs).

In this new world, **the memory capacity available to the AI (the so-called context window) becomes the most valuable commodity**, and **tokens are the currency**. When we waste this memory, it doesn’t just cost us money in API fees. It has been proven that under the weight of long texts, AI loses focus, easily forgets crucial context, and makes silly mistakes in the code.

This article breaks down in detail how AI actually reads text, where invisible leaks occur in both code and data, and how to use simple habits to save 10 % to 40 % of your digital assistant’s memory.

---

## 1. How Artificial Intelligence (Mis)understands Human Aesthetics

To understand why visually beautiful code can needlessly devour an AI’s memory, we need to look at how AI processes text in the first place. Models don’t read text letter by letter or word by word. They use systems called **tokenizers**—algorithms that chop text into smaller logical chunks, or **tokens**. One token corresponds to roughly four characters of English text.

*Note: The specific token counts in the examples below are illustrative. The exact breakdown differs from model to model and version to version — newer models have increasingly optimized tokenizers and may already partially address some of the inefficiencies described. The underlying principles, however, remain valid.*

The catch is that these systems were trained on standard internet texts and finished code from public repositories. Any atypical whitespace (extra spaces) cannot be processed efficiently, forcing the tokenizer to split them up into complex fragments.

### A. Indentation: The Battle of Spaces vs. Tabs
Many programming style guides strictly require using four spaces for text indentation. AI systems are indeed optimized to perceive four consecutive spaces as a single chunk (token). However, as soon as your code reaches deeper levels of nesting (such as nested loops or conditional blocks), this magic breaks down.

If a line is indented at the fourth nesting level, that means 16 consecutive spaces. The AI rarely reads these as four clean chunks. Due to statistical probabilities within its system, these 16 spaces break down into an odd combination (e.g., a block of 4 spaces + a block of 2 spaces + 2 separate spaces + another block of 4 spaces). As a result, **you waste 5 to 8 tokens per line just on the whitespace at the beginning**.

In contrast, an actual tab character (`\t`) is registered in the AI’s system as **one single, independent chunk**.

```text
Indentation at the 4th nesting level:
[Using spaces] --> [    ] [    ] [  ] [ ] [ ] [    ]  --> 6 tokens (inefficient)
[Using tabs]   --> [\t] [\t] [\t] [\t]                --> 4 tokens (always 1:1)
```

In an average 500-line file, switching to pure tabs saves hundreds of tokens. If your AI assistant scans your entire project folder, we are talking about saving tens of thousands of tokens in a single afternoon.

### B. Column Alignment: Wasted Beauty
Many programmers like to align equals signs or values vertically to make the code look like a neat table:

```javascript
const shortName      = "low";
const mediumName     = "medium";
const reallyLongName = "high";
```

While this looks great to the human eye, it is pure waste for an AI. Six empty spaces were created between the text `shortName` and `=`. The AI cannot cluster them efficiently, creating several useless extra tokens.

Even worse is the **domino effect in code history**. If you add a new variable with a very long name to this block in the future, you will have to shift the alignment of all surrounding lines twenty spaces to the right for the sake of aesthetics.
1. **For you:** A change that takes a few seconds.
2. **For the version control system (Git):** A change on every single line. The system reports that the entire block of code has modified.
3. **For the AI:** A total fracture of its memory. Modern AI models use smart caching. If they detect that the code text hasn’t changed, they load it instantly and at a huge discount. However, as soon as you shift the spaces on five surrounding lines, this cache is invalidated, and you pay to analyze the whole block all over again.

## 2. Languages Under the Microscope: Python, HTML, and Markdown Tables

This principle of wasting space manifests across all technologies, often with unexpected side effects.

### Python: When Spaces Cause Errors
Python is unique because it defines code blocks using the exact number of spaces at the beginning of a line rather than brackets. When an AI generates a longer Python script, it sometimes “miscounts” while outputting dozens of spaces. If it generates seven spaces instead of eight on a single line, the resulting code fails to run (throwing an `IndentationError`).

If you teach the AI to use tabs in your project, this issue virtually disappears. It is much easier for a model to calculate “generate 2 tabs” than “generate 8 spaces.” The code becomes safer, and the AI generates it faster.

### Markdown Tables: Huge Memory Hogs
When you request a table from an AI in a chat, or send a table to it yourself in Markdown format, humans tend to visually align it so that the columns line up perfectly:

```markdown
| Name       | City        | Age |
|------------|-------------|-----|
| John       | Prague      | 26  |
| Frank      | Bratislava  | 34  |
```

All those extra dashes and spaces keeping the columns aligned are nice for display in a text editor, but they are a disaster for AI memory. Markdown doesn’t care at all whether the columns align visually. This notation works exactly the same way:

```markdown
| Name | City | Age |
|---|---|---|
| John | Prague | 26 |
| Frank | Bratislava | 34 |
```

The resulting table renders exactly the same way on screen, but **you save up to half the tokens**. If you have the AI generate a large overview, you will save a ton of time and memory by forbidding it from visually padding Markdown tables with spaces.

### HTML and XML: The Worst Combination
Hypertext Markup Language (HTML) and Extensible Markup Language (XML) are the most taxing formats for AI memory. They combine two issues: they are highly verbose (every element must have a start and end tag, e.g., `<user></user>`) and they tend to be deeply nested. At the fifth level of nesting with standard spaces, you are sending twenty empty characters before every single word.

If you are having an AI analyze a downloaded web page, it is always worth stripping it of unnecessary line breaks and empty spaces before sending.

## 3. UPPERCASE LETTERS: The Underestimated Money Sink

The difference in how an AI perceives the words `select`, `SELECT`, and `Select` is shocking to most people. Because text on the internet is written primarily in lowercase, the AI has cheap, single-word chunks ready for common words (like programming commands or function names).

However, as soon as you turn on Caps Lock and write a word in all caps, the system cannot find it in its dictionary and must **painfully piece it together from smaller fragments**.

### How AI Perceives Letter Casing:

* **`select`** → **1 chunk**: `[select]`
* **`SELECT`** → **2 chunks**: `[SE]` + `[LECT]`
* **`migration`** → **1 chunk**: `[migration]`
* **`MIGRATION`** → **3 chunks**: `[M]` + `[IGR]` + `[ATION]`

If you write database scripts in the traditional style where all keywords are strictly uppercase (`CREATE TABLE USERS`), you consume **twice the amount of memory** on those words compared to converting everything to lowercase (`create table users`).

The situation is similar for compound variable names (such as alternating cases in `transactionId`). A capital letter in the middle of a word acts as a cut, causing the system to split the word into two parts. If possible, using lowercase letters separated by underscores (`transaction_id`) or abbreviations (`tx_id`) is the most stable approach for saving tokens in databases, code, and configurations.

## 4. Case Study: Database Schema Description (SQL vs. DBML)

If you develop database applications (for instance, using modern tools that build an API directly on top of the database), your AI assistant needs to know your table structure in detail to help you. Throwing a complete raw SQL export (`CREATE TABLE…`) at it is the fastest way to clog its memory.

Here is a clear comparison of how the same schema can be written in standard SQL versus the more compact, modern DBML format. By the way, if you work with PostgreSQL and don’t want to rewrite schemas manually, you can use a simple CLI tool [pg_dbml](https://pg_dbml.80.cz) to automatically export your entire structure into clean DBML.

### SQL Version (Verbose, approx. 45 tokens)
```sql
CREATE TABLE "users" (
  "id" SERIAL PRIMARY KEY,
  "username" varchar(50) NOT NULL,
  "role_id" integer NOT NULL,
  CONSTRAINT "fk_users_role" FOREIGN KEY ("role_id") REFERENCES "roles" ("id")
);
```

### DBML Version (Compact, approx. 18 tokens)
```dbml
Table users {
  id int [pk, increment]
  username varchar(50)
  role_id int
}
Ref: users.role_id > roles.id
```

### Why the Leaner Format (DBML) Saves Over 60 % of Memory?
1. **Clean Text:** It avoids constantly repeating quotes, which the AI often chops off as separate characters.
2. **Simple Relationships:** Writing a foreign key constraint in SQL (`CONSTRAINT…`) consumes roughly 15 tokens. In modern DBML, a single, short line is enough: `Ref: users.role_id > roles.id` (6 tokens).
3. **Clarity:** It is much easier for an artificial intelligence to grasp relationships between tables when they are written cleanly in one place, rather than having to extract them from the insides of complex SQL statements.

## 5. How to Automate It So Your Eyes Don’t Suffer

The goal of these rules is not to force you to write ugly or unreadable code. The goal is to configure your development environment so that the code looks great to you in the editor, but automatically cleans itself of unnecessary bloat (extra spaces) and shrinks to a minimum when saved to disk. This is called **line-level cleaning**—line breaks are preserved, so the code remains perfectly readable in your git history, but the empty filler is gone.

### Step 1: Set Up an Automatic Cleaner (SQLFluff for SQL)
To format database files, you can use the free tool `SQLFluff`. The correct configuration ensures that the code is stripped of excess spaces and converted to lowercase. To make debugging rules easy, you can visually test and configure the entire structure using [SQLFluffUI](https://sqlfluffui.80.cz), which saves you time spent manually tweaking configuration texts.

Just create a configuration file in your project with these rules:

```ini
[sqlfluff:indentation]
# We use tabs for 100% predictable savings
indent_unit = tab
tab_width = 4

[sqlfluff:rules:layout.spacing]
# Enforces exactly 1 space around operators, erasing visual columns
force_spacing = true

[sqlfluff:rules:capitalisation.keywords]
# Converts all SQL keywords to more efficient lowercase
capitalisation_policy = lowercase
```

### Step 2: Automatic Execution on Save
So you don’t have to think about formatting, you can set up automated actions on save in your editor (e.g., VS Code). The code cleans itself a second before it is committed to history. Your AI assistant will then see only this optimized version in the project.

This works similarly for data files (e.g., JSON configurations). Instead of an expanded format stretched over fifty lines, you can let them automatically compress so that each self-contained section sits on one compact line without internal spacing.

## 6. Taming Your AI Assistant via Custom Rules

If you use assistants that navigate your project autonomously, you can adjust their behavior using a rules file. Most of them read a rules file located at the root of your project upon startup — the filename depends on the specific tool (`CLAUDE.md` for Claude Code, `AGENTS.md` for OpenAI Codex, and others). Check your assistant’s documentation.

You can provide them with explicit instructions in this file to conserve their own memory and, importantly, to avoid sending excessively long responses (since output tokens from an AI are significantly more expensive than input tokens).

Here is a simple block of rules you can just copy into the file:

```markdown
## Rules for Token and Memory Savings

When working on this project, strictly adhere to the following rules to conserve the context window and speed up responses:

### 1. Code Reading and Search Strategy
- **Targeted Reading:** Never read entire large files (>500 lines) if you only need to see one specific function. Use tools to read specific line ranges instead.
- **Efficient Searching:** Prefer searching precisely using text filters (grep/regex) over blindly opening files to inspect their structure.

### 2. Response and Code Generation Rules
- **Be Concise (No Filler):** Do not repeat my prompt and skip pleasantries ("Sure, I'd be happy to help you with that..."). Start directly with the answer or the code block.
- **Send Only Changes (Truncated Code):** When showing code modifications in chat, never print the entire file again. Show ONLY the lines that changed. Replace untouched parts of the code with a comment like `// ... rest of the code ...`.
- **Code Style:** When generating code, exclusively use a single tab (`\t`) for indentation. Never use spaces for visual column alignment.
```

## Summary Table of Savings

The following overview demonstrates the real impact these minor changes have on the amount of data you need to feed into the AI:

| Code/Data Element | Original State | New, Efficient State | Real AI Memory Savings |
| :--- | :--- | :--- | :--- |
| **Line Indentation** | 4 spaces | 1 tab (`\t`) | **15 % – 25 %** of total whitespace |
| **Column Alignment** | Multiple spaces for aesthetics | Always exactly 1 space | **5 % – 10 %** per code block |
| **Casing Size (SQL)** | `CREATE TABLE` (Upper) | `create table` (Lower) | **30 % – 50 %** of keywords |
| **Markdown Tables** | Wide, aligned columns | Compact layout without spaces | **40 % – 60 %** of table size |
| **Database Description**| Raw SQL DDL Dump | DBML format | **50 % – 70 %** of entire schema |
| **Data Transmission** | Expanded “pretty” JSON | Minified JSON (on 1 line) | **60 % – 90 %** of total data volume |

## Conclusion

Optimizing code for artificial intelligence is becoming a valuable new skill for every modern creator. You don’t have to change how you see the code yourself—just set up automatic formatters in your editor correctly. A developer or analyst who can maintain a low “token footprint” gains a massive advantage: their AI assistant operates faster, commits fewer errors, handles larger sections of the application at once, and running the whole system costs a fraction of the original price.
